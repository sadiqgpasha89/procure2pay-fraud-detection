Use case · Finance & Internal Audit

Stop procure-to-pay fraud before the money leaves.

An agentic system that scores every invoice in about 80 ms, escalates only the suspicious few to AI investigators, and hands analysts an evidence-cited case file where every claim is hash-verified against the source system.

The problem

P2P fraud is boring in the way that makes it expensive. Nobody hacks anything. Someone asks accounts payable to “update our banking details”, from a look-alike domain. Someone splits a large invoice to slip under an approval limit. The payment is released, and the money is gone.

Bank-detail diversion

A vendor’s account number is changed shortly before a payment run, often via spoofed e-mail.

Split invoices

One large invoice is cut into several smaller ones below the approval threshold (smurfing).

Shell vendors

Fictitious suppliers controlled by insiders or outsiders, onboarded with thin due diligence.

Collusion

Approvers and vendors working together to authorise payments that should not clear.

Phantom deliveries

Goods receipts recorded for goods that never arrived, so the three-way match passes.

Contract overbilling

Invoiced prices exceed what the contract allows. Spotting it means reading the contract.

Duplicates

The same invoice resubmitted with small variations to get paid twice.

Sanctioned vendors

Payments to entities on OFAC or PEP lists: a compliance failure, not just a financial loss.

The challenge: catch all of this in near real time, during high-volume payment runs, without drowning the AP team in false alarms, and with an audit trail that satisfies SOX and GDPR reviewers.

The approach: three tiers, cheapest first

Put the fast, deterministic things in front of the slow, fallible one. The language model only runs on the ~7–10% of invoices the earlier tiers escalate, and it never decides what happens to the money.

Tier 1 · Rules

Hard policy checks

Exact duplicates, sanctions hits, bank changes within 72 hours of a payment run, invoices above PO ceilings.

Microseconds · deterministic · immediate BLOCK

Tier 2 · Machine learning

Behavioural risk score

LightGBM classifier, Isolation Forest and graph features score each invoice 0–1, with TreeSHAP showing which features drove it.

~80 ms P50 · explainable · APPROVE / HOLD

Tier 3 · Agents

Evidence-cited investigation

An investigator agent fans out to a graph analyst and a document auditor, each using read-only tools, then compiles a case dossier.

~3 s · async · human sign-off

Architecture

Ten small services built from one container image. Agents talk to each other over A2A and to data through read-only MCP tool servers, on Google ADK.

Hot path

Gateway → scoring → decision. No LLM involved, so a model outage never blocks a payment run.

Cold path

Only escalated invoices trigger the investigator, asynchronously. The result lands in the case queue for an analyst.

Audit trail

Every decision, dossier and human sign-off is written to a tamper-evident hash-chained ledger by a single writer.

What the investigator does

  1. Fan outSpecialists receive only invoice_id and vendor_id, not the ML score, so they corroborate independently.
  2. Re-verifyEvery cited record hash is re-derived by the MCP server that owns the data. Unverifiable claims are dropped.
  3. NarrateThe language model writes prose from verified findings only.
  4. GuardrailCitation and grounding checks run over the narrative.
  5. DecideA deterministic policy function picks the recommended action. A human signs off.

Design decisions that matter

The parts that make this safe to put near money.

1

The LLM never decides money

The action comes from a pure policy function of rule violations, ML score and verified findings. A failed or empty investigation can never yield an auto-approval.

2

Evidence is content-addressed

Each tool result carries (source, record_id, sha256). Citations are re-verified against the owning server before they reach the dossier.

3

No anchoring on the ML score

Specialist agents never see it, so their evidence is independent.

4

Retrieved text is untrusted

Instruction-like spans in e-mails and documents are stripped at the MCP boundary and reported as a finding. 6 of 6 planted injections were flagged, none auto-approved.

5

No train/serve skew

One feature builder serves training and scoring, always point-in-time.

6

Ground truth is unreachable by agents

Labels live in a separate store, and a test asserts no tool or agent module can import it.

7

Fail closed, stay up

Verification outages add risk rather than waving invoices through. An audit outage is logged but does not stop decisions.

Weak spots, reported rather than hidden. Split-invoice recall is only 57%, because the first invoice of a split looks normal when it arrives. Near-duplicates are caught only within a 7-day window. With a small local model (gemma4:e4b), analysis was looser than the reference model, and hash verification proves a record exists unchanged, not that the model read it correctly. Treat a larger model as the production default.

Run it yourself

Everything runs on a laptop with synthetic data and no API key.

git clone https://github.com/sadiqgpasha89/procure2pay-fraud-detection
cd procure2pay-fraud-detection

make setup       # uv venv + dependencies (Python 3.12)
make bootstrap   # synthetic data, features, models, RAG index (~25 s)
make up          # 10 services: gateway :8100, console :8102

curl -s localhost:8100/v1/evaluate \
  -H 'content-type: application/json' \
  -d '{"invoice_id":"INV-004065","wait_for_investigation":true}' \
  | jq .dossier.agent_narrative
